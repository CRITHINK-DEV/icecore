# Spike S1: write mechanisms

Story 3d0b80bf (S12). Measured on 31 Oct 2026 in the sandbox (Snowflake 10.39.101, dbt-core 1.8.10, dbt-snowflake 1.8.4).
The database ICECORE_SANDBOX has `EVENT_TABLE = ICECORE_SANDBOX.TELEMETRY.EVENTS`, `LOG_LEVEL = INFO` and `TRACE_LEVEL = ALWAYS`.
The account keeps the default event table `SNOWFLAKE.TELEMETRY.EVENTS`. The role ICECORE_CI reads only the sandbox table.

Raw measurements are in `spikes/results/s1.json`, one key per probe.

- The probes are in `integration_tests/macros/spikes/s1_*.sql`.
- The tests are in `integration_tests/tests/spikes/test_s1_write_mechanisms.py` (E1, E2, E3, routing) and
  `test_s1_emit_procedure.py` (the Gate 1 procedures).
- Every probe goes through `dbt run-operation`, so every statement reaches Snowflake through `run_query`, exactly as the package
  would send it.

Final sandbox run of both files: **32 passed, 2 skipped in 2476.55 s**. The tables below quote that run unless they say otherwise.
Statements marked *(exploration)* come from ad-hoc probes made with the connector, not from `s1.json`.

## Headline

**Gate 1 outcome, decided by the owner on 31 Oct after these measurements: option B, two persisted procedures.**

`icecore.setup` creates both in `<target_db>.ICECORE_OBS`, and hooks and tests `CALL` them through `run_query`, guarded:

- **`ICECORE_EMIT(events ARRAY)`**: SQL, `EXECUTE AS OWNER`. It writes one SPAN_EVENT per event through `SYSTEM$ADD_EVENT`, with
  `SCOPE` = `global`. It carries the structured events.
- **`ICECORE_EMIT_RUN(spans ARRAY)`**: Python, `EXECUTE AS OWNER`. It writes custom spans with explicit start and end times, with
  `SCOPE` = `icecore`. It carries a run's node spans in one CALL. It is persisted rather than temporary because dbt threads use
  separate sessions.

Records go to the event table of the procedures' database and inherit that database's levels.

Rejected:

- option A: anonymous blocks, plus session levels, plus `EVENTS_VIEWER` on the shared account table;
- E2 as an anonymous Python procedure;
- E3, the hybrid table.

What the measurements show:

1. **Anonymous statements never write to a database's event table.**
   - This covers both a Snowflake Scripting block (`EXECUTE IMMEDIATE $$ ... $$`) and an anonymous Python procedure
     (`WITH p AS PROCEDURE ... CALL p(...)`).
   - Every call succeeds, and `assert_no_events` sees nothing in `ICECORE_SANDBOX.TELEMETRY.EVENTS` for 180 s.
   - That holds with session levels OFF or INFO/ALWAYS, with or without a current database, and with `USE DATABASE` inside the block.
   - According to the lead's ACCOUNTADMIN check (below, LOG records only), they land in the account table as `STATEMENT`, and only
     when the session sets levels.
2. **Records from a procedure land in the procedure's database's event table** as `PROCEDURE`, with `snow.database.name` and
   `snow.query.id`. This is true of temporary procedures and of persisted procedures, of SQL and of Python.
3. **Through a procedure, every acceptance criterion passes.** That means 100/100 records, typed attributes, byte-identical
   escaping, success with levels OFF, and records kept after a rollback.
4. **Python gives what SQL cannot:**
   - `SCOPE` = `icecore`;
   - LOG records with attributes;
   - custom spans whose **explicit start and end times are kept to the millisecond**, so a node's span can carry its dbt timings
     when written after the fact.
5. **Python packages must be pinned** (see [Python packages](#python-packages)).

## Routing: which table receives the record

This is the decisive fact for Gate 1. The routing probe is `test_s1_routing_by_database_context`. Each variant emits one span
event and one log with the session at `LOG_LEVEL = INFO` and `TRACE_LEVEL = ALWAYS`.

The test asserts what the sandbox table shows:

- 0 rows for every anonymous variant;
- 2 rows (LOG + SPAN_EVENT, `PROCEDURE`, `snow.database.name = ICECORE_SANDBOX`) for the two procedure variants.

The account-table column comes from the lead's ACCOUNTADMIN query on the 31 Oct run, kept in `s1.json` as
`routing_checked_by_lead`, with rows under `routing_account_table`. The lead later found that the query's `value::string`
predicate dropped every row whose `VALUE` is NULL, which is every SPAN and SPAN_EVENT row. **Account-table statements here are
therefore limited to LOG records.** A re-run with `coalesce(value::string, '')` needs ACCOUNTADMIN, because ICECORE_CI cannot
read `SNOWFLAKE.TELEMETRY` and the lead declined a grant for now.

The lead also read the account table for the main-suite anonymous runs made with session levels OFF: 100 logs (18964ee6), the
rollback probe (76a9df52) and the others. **No LOG landed in either table.**

A separate check by the lead used `EXECUTE IMMEDIATE $$BEGIN SYSTEM$LOG_INFO(...); SYSTEM$ADD_EVENT(...); END;$$` over a session
whose database was ICECORE_SANDBOX:

- With only the database levels set, no LOG landed anywhere after 240 s.
- With session levels set, the LOG landed in the account table as STATEMENT, without a database.

**The rule these results establish:**

1. Anonymous blocks and anonymous Python procedures take their levels from the **session**. On the LOG evidence, when they do
   emit, the records go to the **account** event table, attributed to no database (`STATEMENT`), whatever the session's database.
2. Only an object that lives in a database (a procedure, and by the same logic a UDF) is routed to that database's event table
   and inherits that database's levels.
3. An anonymous block that calls such a procedure is fine: the records belong to the procedure. This is what makes the guard
   block in option B safe.

- **Record shape (procedure).** `RESOURCE_ATTRIBUTES` keys are `db.user`, `snow.database.id`, `snow.database.name`,
  `snow.executable.id`, `snow.executable.name`, `snow.executable.type`, `snow.owner.id`, `snow.owner.name`, **`snow.query.id`**,

  `snow.user.id`, `snow.warehouse.id`, `snow.warehouse.name` and `telemetry.sdk.language` (`sql` or `python`). Python also adds
  `snow.executable.runtime.version`. `snow.query.id` is present on every row and is the query id of the `CALL`.
- **Trace grouping.**
  - Each `CALL` is its own trace, and the trace id's first 8 hex characters equal the query id's first 8.
  - Two consecutive run-operations gave two trace ids (`temp_procedure.trace_grouping`, `shared_trace: false`).
  - All records from one `CALL` share one trace.
  - A dbt invocation therefore has no common trace: `dbt.invocation_id` must be an attribute on every record.
  - *(exploration)* Python custom spans get their own span ids under the procedure span, linked by `parent_span_id`.
- **SQL record names.** `SYSTEM$ADD_EVENT('icecore.probe', ...)` gives `RECORD:name = 'icecore.probe'` with `SCOPE.name = 'global'`.
  SQL cannot set `SCOPE`, so ICECORE_EMIT relies on the `icecore.` record-name prefix.
- **Levels.**
  - With `ALTER SESSION SET LOG_LEVEL = 'OFF', TRACE_LEVEL = 'OFF'`, every probe still returned success, and procedure records
    **still landed** (2 LOG, 2 SPAN, 2 SPAN_EVENT): the database's INFO/ALWAYS wins over the session's OFF.
  - A user cannot silence icecore by session, so the on/off switch has to be the package var.
  - The plan expected "0 rows land" with levels OFF. The test asserts success (the acceptance criterion) and records what landed.
- **Rollback.**
  - The probes open `BEGIN TRANSACTION` and check that `CURRENT_TRANSACTION()` is the same before and after the emission.
  - They emit, then run `ROLLBACK`. The records landed.
  - Temporary procedures are created before `BEGIN`, because `CREATE` is DDL and would commit the open transaction.
- **Python noise** *(exploration)*. Every Python procedure call also writes about 3 INFO LOG rows from
  `snowflake.connector.connection` and `snowflake.snowpark.session`, at session start. They carry no icecore tag, but they cost
  ingestion.
- **Timestamps written after the fact.**
  - In the tests, spans written 2 hours back (`e2_python_span_timings`) and 1 hour back (`proc.emit_run_python`) kept their exact
    times.
  - *(exploration)* A span 5 days back kept them too.
  - Readers that window on `TIMESTAMP` must allow for this.

## Escaping

`s1_sql_literal` builds a single-quoted literal:

- It escapes the backslash first, then the quote.
- It turns `$` into `\x24`, so a value can never close a `$$` block.
- It turns CR and LF into `\r` and `\n`.

Values reach SQL only as literals: as `DECLARE ... DEFAULT` values in the anonymous block, or as `CALL` arguments to a static
procedure body. Attributes travel as JSON (`tojson`) parsed with `PARSE_JSON`.

The message `it's a \ test` + newline + `new line é ü 漢 $$ end of block? $$` and the attribute `$$ end of block? $$` round-tripped
byte-identical for the E1 log message, the E1 event attribute, the E2 log message and the E2 log attribute
(`temp_procedure.escaping`), and through ICECORE_EMIT (`proc.escaping`). Through the anonymous path all three calls succeed with
these values (`anonymous.escaping`), and nothing lands.

## Consequences

**E1, SQL span events from anonymous blocks (as planned): rejected.**

- Records never reach the database's event table.
- They emit at all only if the session sets levels, and the database's settings are ignored.
- When they emit, the LOG evidence puts them in the account table as `STATEMENT`, with no database. Reading that table needs
  `SNOWFLAKE.EVENTS_VIEWER` or ACCOUNTADMIN.

**E2, anonymous Python procedure (as planned): rejected, for the same routing and levels reasons.** Its packages also proved
unstable (see above).

**E1 and E2 through a procedure: work.**

- **Temporary procedure.** It lives only in the session and costs a `CREATE` plus a `DROP` per emission: CREATE 68–221 ms and
  DROP 45–71 ms in the final run, and up to 874 ms and 386 ms in an earlier run. It needs `CREATE PROCEDURE` on the target schema
  at run time. dbt threads use separate sessions, so each would have to create its own.
- **Persisted procedures** created by `icecore.setup`. There is no per-call create or drop. They are package-owned objects, which
  the spec's list of allowed objects did not include. **Gate 1 chose these** (option B).

**E3, hybrid table: works, but it loses records on rollback and is an owned table.** It also contradicts principle 1. Keep it only
as the documented last resort.

**Views.**

- Records are attributed to and routed by the database that owns the procedures: `<target_db>`.
- The views read the event table active for that database: `SHOW PARAMETERS LIKE 'EVENT_TABLE' IN DATABASE <target_db>`. If the
  database has none, that is the account's table, read through `SNOWFLAKE.TELEMETRY.EVENTS_VIEW` on Standard edition.
- They filter on `snow.executable.name LIKE 'ICECORE_EMIT%'` with the icecore identity: record names `icecore.%` for ICECORE_EMIT
  span events, and `SCOPE:name = 'icecore'` for ICECORE_EMIT_RUN spans.
- Spans written after the fact carry dbt node times, so incremental reads must window on more than `TIMESTAMP` (for example,
  ingestion order or a generous lookback).

## Gate 1 outcome and recommendation

The owner decided **option B**: two persisted procedures in `<target_db>.ICECORE_OBS`, created by `icecore.setup`, both
`EXECUTE AS OWNER`, and called guarded through `run_query`.

- **`ICECORE_EMIT(events ARRAY)`** (SQL) writes span events, one `SYSTEM$ADD_EVENT` per event, with SCOPE `global` and the
  `icecore.` name prefix.
- **`ICECORE_EMIT_RUN(spans ARRAY)`** (Python, pinned packages) writes a run's custom spans with explicit times, with SCOPE
  `icecore`.

This spike recommends it. The comparison it rests on:

| Option | Lands in the database's event table | Levels | Typed attributes | SCOPE | Spans with dbt times | Rollback | Missing or no grant | Cost per 100 records | Owned object |
|---|---|---|---|---|---|---|---|---|---|

| **B / ICECORE_EMIT_RUN** (Python, **chosen**) | **yes**, `PROCEDURE` | inherited | yes, exact | **`icecore`** | **yes**, explicit start and end kept | not measured | guard as above | **2.82 s server in 1 CALL** (100 spans) | one procedure |
| E1 / E2 through a temporary procedure | yes | inherited | yes | E2 gives `icecore` | E2 yes | kept | not measured | E1 about 0.5 s, E2 about 2.8 s (create + call + drop) | none persistent; `CREATE PROCEDURE` at run time, per session |

| E3 hybrid table | n/a (a table) | n/a | yes | n/a | n/a | **lost** | not measured | about 0.4 s INSERT | a table |

Consequences for building option B:

- **Batch, in chunks.**
  - ICECORE_EMIT: one CALL with an ARRAY of events instead of one CALL per event (0.73 s against 78 s for 100 events).
  - S2 shows a CALL keeps only its last 128 events and silently drops a batch of about 1 MB, so ICECORE_EMIT batches go in
    chunks of **at most 100 events and 512 KB** (S2.md, `spikes/GATE1.md`).
  - ICECORE_EMIT_RUN: S2 landed 200 spans and 4 MB in one CALL.
- **Guard every CALL.**
  - Use an anonymous block with `EXCEPTION WHEN OTHER` and turn the error into a dbt warning.
  - A bare `CALL` to a missing procedure fails the run-operation.
  - Missing and not-authorized return the same error (2141).
- **The guard block itself is anonymous.** Its own records, if the session sets levels, go to the account table. The events
  always belong to the procedure.
- **Identity.**
  - ICECORE_EMIT records: `RECORD_TYPE = 'SPAN_EVENT'`, name prefix `icecore.`, `snow.executable.name LIKE 'ICECORE_EMIT(%'`.
  - ICECORE_EMIT_RUN records: `SCOPE:name = 'icecore'`.
- **Pin ICECORE_EMIT_RUN's packages** (`opentelemetry-api==1.38.0` today), and have the doctor macro check that a test CALL succeeds.

**Open points for later spikes and stories:**

1. **S3:** lag, concurrency and hook coverage through both procedures.
2. Grants to the dbt role: USAGE on `ICECORE_OBS` and on both procedures. The guard keeps a missing grant from failing a run, but
   telemetry is then lost, so the doctor macro should check the grants.
3. Rollback through the persisted Python procedure was not measured.
4. Behaviour on dbt Fusion, dbt Cloud and `EXECUTE DBT PROJECT` is not measured here.
5. "Event table missing" (Review Focus 2) cannot be reproduced with the CI role. With no database event table, procedure records
   would go to the account table.
6. Whether ICECORE_CI (and the doctor macro) may read the account table through `SNOWFLAKE.EVENTS_VIEWER`. With that grant, the
   account-table side of the routing probe could be asserted for SPAN and SPAN_EVENT records too.

## Deviations from the Phase 1 plan (Task 3)

- Every probe takes an optional `via` (`'anonymous'` by default, as planned; `'temp_procedure'` added). The nine planned tests are
  parametrized over it, so each planned test name exists twice, `[anonymous]` and `[temp_procedure]`.
- The `[anonymous]` cases assert the measured behaviour instead of the plan's expectation: every call succeeds, and
  `assert_no_events` holds for 180 s.
