# Spike S1: write mechanisms

Story 3d0b80bf (S12). Measured on 31 Oct 2026 in the sandbox (account RK01532, Snowflake 10.39.101,
dbt-core 1.8.10, dbt-snowflake 1.8.4). The database ICECORE_SANDBOX has `EVENT_TABLE = ICECORE_SANDBOX.TELEMETRY.EVENTS`,
`LOG_LEVEL = INFO` and `TRACE_LEVEL = ALWAYS`. The account keeps the default event table `SNOWFLAKE.TELEMETRY.EVENTS`.
The role ICECORE_CI reads only the sandbox table.

Raw measurements are in `spikes/results/s1.json` (one key per probe). The probes are in `integration_tests/macros/spikes/s1_*.sql`
and the tests in `integration_tests/tests/spikes/test_s1_write_mechanisms.py`. Every probe goes through `dbt run-operation`, so
every statement reaches Snowflake through `run_query`, exactly as the package would send it.

## Headline

1. **Anonymous statements never write to a database's event table.** A Snowflake Scripting block (`EXECUTE IMMEDIATE $$ ... $$`)
   and an anonymous Python procedure (`WITH p AS PROCEDURE ... CALL p(...)`) both run successfully. Not one of their records
   reached `ICECORE_SANDBOX.TELEMETRY.EVENTS`. That held with or without a current database, with `USE DATABASE` run inside the
   block, and with session levels OFF or INFO/ALWAYS.
   The lead's check as ACCOUNTADMIN (below) shows where these records go. With session levels set, they land in the account's
   event table `SNOWFLAKE.TELEMETRY.EVENTS` with `snow.executable.type = STATEMENT` and no `snow.database.name`, whatever the
   session's database. With only the database levels set, they land nowhere.
2. **Records from procedures do land in the database's event table.** A temporary procedure created in the target schema
   (`CREATE TEMPORARY PROCEDURE <db>.<schema>.<name>`, then `CALL`, then `DROP`) puts every record there. Each record carries
   `snow.database.name`, `snow.executable.type = PROCEDURE` and `snow.query.id`.
   Through that path, every acceptance criterion passes for both E1 and E2: 100/100 records, typed attributes, byte-identical
   escaping, success with levels OFF, and records kept after a rollback.
3. **E2 (Python) delivers what the spec assumed.** It gives LOG records with attributes, `SCOPE.name = 'icecore'` and custom spans.
   Those spans can take **explicit start and end times**, so a node's span can carry its real dbt timings when it is written after
   the fact.
   E1 (SQL) has no LOG attributes: `SYSTEM$LOG` takes only a message. Its `SCOPE.name` is `global` on span events and `null` on
   logs, and it has no custom spans.

## Routing: which table receives the record

This is the decisive fact for Gate 1. The routing probe is `test_s1_routing_by_database_context`. Each variant emits one span
event and one log with the session at `LOG_LEVEL = INFO` and `TRACE_LEVEL = ALWAYS`.

- The sandbox columns come from the probe, which read the sandbox table 60 s after the baseline variant had landed.
- The account-table column comes from the lead, who on 31 Oct ran a query as ACCOUNTADMIN that read both tables and matched on
  the run_id.
- ICECORE_CI cannot read `SNOWFLAKE.TELEMETRY.EVENTS` (`Schema 'SNOWFLAKE.TELEMETRY' does not exist or not authorized`), so the
  probe records `not readable` for that side.
- The lead declined a grant for now. Whether ICECORE_CI gets `SNOWFLAKE.EVENTS_VIEWER` is a Gate 1 decision.
- The per-run rows are in `s1.json` under `routing_account_table`, and the run_ids under `run_ids`.

The main-suite anonymous runs were made with the session at dbt's default levels (OFF), with only the database at INFO/ALWAYS.
They are: 100 logs (18964ee6), 100 span events (a7d2e228), `SET_SPAN_ATTRIBUTES` (858c690b) and the rollback probe (76a9df52).
They landed **in neither table**. The temporary-procedure controls (e1 log 2ece23ea and Python logs 6ca7668f) put 100 LOG rows each
in the sandbox table, as `PROCEDURE` with `snow.database.name = ICECORE_SANDBOX`.

The lead also checked separately, on 31 Oct. An anonymous `EXECUTE IMMEDIATE $$BEGIN SYSTEM$LOG_INFO(...);
SYSTEM$ADD_EVENT('icecore.harness_probe', {...}); END;$$` was sent over a session whose database was ICECORE_SANDBOX.

- With only the database levels set, nothing landed anywhere after 240 s.
- With session levels set, one LOG and one SPAN_EVENT landed in the account table as STATEMENT, without a database. The run_id
  attribute was intact.

**The rule these results establish:**

1. Anonymous blocks and anonymous Python procedures emit only when the **session** sets `LOG_LEVEL` / `TRACE_LEVEL`.
2. When they do emit, the records always go to the **account** event table, attributed to no database (`STATEMENT`), whatever
   the session's database or a `USE DATABASE` inside the block.
3. Only an object that lives in a database (a procedure, and by the same logic a UDF) is routed to that database's event table
   and inherits that database's levels.
4. An anonymous block that calls such a procedure is fine: the records belong to the procedure.
5. With session tracing on, the outer statement still adds its own SPAN rows to the account table.
6. Attributes on SPAN_EVENT survive on both paths.
7. An anonymous Python procedure works only with PACKAGES `snowflake-snowpark-python` + `opentelemetry-api`. Adding
   `snowflake-telemetry-python` makes the `snowflake.snowpark` import fail.

A bisection on 31 Oct showed:

Other observations:

- **Record shape (temp procedure).** `RESOURCE_ATTRIBUTES` keys are `db.user`, `snow.database.id`, `snow.database.name`,
  `snow.executable.id`, `snow.executable.name` (for example `S1_LOG_<RUN_ID>(MSG VARCHAR, RUN_ID VARCHAR, N NUMBER):VARCHAR`),
  `snow.executable.type`, `snow.owner.id`, `snow.owner.name`, **`snow.query.id`**, `snow.schema.id`, `snow.schema.name`,
  `snow.session.id`, `snow.session.role.primary.id`, `snow.session.role.primary.name`, `snow.user.id`, `snow.warehouse.id`,
  `snow.warehouse.name` and `telemetry.sdk.language` (`sql` or `python`). Python also adds `snow.executable.runtime.version`.
  `snow.query.id` is present on every row and is the query id of the `CALL`.
- **Trace grouping.**
  - Each `CALL` is its own trace, and the trace id's first 8 hex characters equal the query id's first 8.
  - Two consecutive run-operations gave two trace ids (`shared_trace: false`).
  - All records from one `CALL` share one trace and one span. The exception is Python custom spans, which get their own span ids
    under the procedure span, linked by `parent_span_id`.
  - A dbt invocation therefore has no common trace: `dbt.invocation_id` must be an attribute on every record.
- **SQL record names.** `SYSTEM$ADD_EVENT('icecore.probe', ...)` gives `RECORD:name = 'icecore.probe'` with `SCOPE.name = 'global'`.
  The SQL path cannot set `SCOPE`, so E1 needs the `icecore.` record-name prefix rule.
- **Levels.**
  - With `ALTER SESSION SET LOG_LEVEL = 'OFF', TRACE_LEVEL = 'OFF'`, every probe still returned success, and procedure records
    **still landed** (2 LOG, 2 SPAN, 2 SPAN_EVENT): the database's INFO/ALWAYS wins over the session's OFF.
  - Anonymous statements, by contrast, follow the session (lead's evidence (a) and (b)).
  - The plan expected "0 rows land" with levels OFF. The test asserts success only (the acceptance criterion) and records what
    landed. A user cannot silence icecore by session, so the on/off switch has to be the package var.
- **Rollback.**
  - `s1_in_rollback` opens `BEGIN TRANSACTION` and checks `CURRENT_TRANSACTION()` before and after the emission (same id).
  - It emits one event and one log, then runs `ROLLBACK`. Both records landed.
  - Temporary procedures are created before `BEGIN`, because `CREATE` is DDL and would commit the open transaction.
- **Python noise.** Every Python procedure call also writes about 3 INFO LOG rows from `snowflake.connector.connection` and
  `snowflake.snowpark.session`, emitted at session start before the handler runs. They carry no icecore tag, but they cost ingestion.
- **Timestamps written after the fact.**
  - A span written with `start_time` / `end_time` 5 days in the past was stored with those exact `START_TIMESTAMP` / `TIMESTAMP`
    values (exploration, 31 Oct).
  - Readers that window on `TIMESTAMP` must allow for this.
  - The S1 test uses 2 hours back so that it stays inside its own 6-hour read window.

## Escaping

`s1_sql_literal` builds a single-quoted literal. It escapes the backslash first, then the quote. It also turns `$` into `\x24`, so
a value can never close a `$$` block, and CR/LF into `\n` / `\r`. Values reach SQL only as literals: as `DECLARE ... DEFAULT`
values in the anonymous block, or as `CALL` arguments to a static procedure body. Attributes travel as JSON (`tojson`) parsed with
`PARSE_JSON`.

`it's a \ test` + newline + `new line é ü 漢`, and `$$ end of block? $$`, round-tripped byte-identical for the E1 log message, the
E1 event attribute, the E2 log message and the E2 log attribute (`temp_procedure.escaping`). Through the anonymous path all calls
succeeded except E2, but nothing landed to compare.

## Consequences

**E1, SQL span events from anonymous blocks (as planned): rejected.**

- Records never reach the database's event table.
- They emit at all only if icecore sets session levels. The CI role can do that, but it overrides the user's choice, and the
  database settings are ignored.
- When they do emit, they land in the account table as `STATEMENT`, with no `snow.database.name`, so they could only be told apart
  by attributes such as `dbt.target` or `dbt.project`.
- On an account that sets an event table per database (Enterprise, as in the sandbox), views reading that table would never see
  them.
- Reading the account table needs `SNOWFLAKE.EVENTS_VIEWER` or ACCOUNTADMIN.

**E2, anonymous Python procedure (as planned): rejected, for the same routing and levels reasons.**

- It lands in the account table as `STATEMENT` (r3).
- With `snowflake-telemetry-python` in PACKAGES, it fails to start.

**E1 and E2 through a procedure in the target database: work.**

- **Temporary procedure** (`CREATE TEMPORARY PROCEDURE` in the dbt target schema, `CALL`, `DROP`). It lives only in the session
  and is not a persistent object. It costs about 0.1–0.3 s for `CREATE` and 0.05–0.15 s for `DROP` per emission, or once per
  session if created once and reused. It needs `CREATE PROCEDURE` on the target schema at run time, which the dbt role usually has
  on its own schema.
- **Persisted procedure** created by `icecore.setup` in the icecore schema. It costs nothing per call, but it is a package-owned
  object. The spec's list of allowed objects (views, ALERT, TASK, Streamlit, one dynamic table) does not include procedures, so
  Gate 1 must decide.

**E3, hybrid table: works, but it loses records on rollback and is an owned table.** It also contradicts principle 1. Keep it only
as the documented last resort.

**Views.**

- Records are attributed to and routed by the database that owns the procedure: the dbt target database, or the icecore schema's
  database if the procedure is persisted.
- The views must read the event table active for *that* database: `SHOW PARAMETERS LIKE 'EVENT_TABLE' IN DATABASE <db>`. If the
  database has none, that is the account's table, read through `SNOWFLAKE.TELEMETRY.EVENTS_VIEW` on Standard edition.
- Views must not assume `SNOWFLAKE.TELEMETRY.EVENTS`, and must not assume the sandbox table.
- Filter on `snow.database.name` together with the icecore identity: `SCOPE:name = 'icecore'` for E2, record names `icecore.%`
  for E1.
- Spans written after the fact carry dbt node times, so incremental reads must window on more than `TIMESTAMP` (for example,
  ingestion order or a generous lookback).

## Recommendation for Gate 1

**E2 executed as a procedure in the target database, a temporary procedure by default.** Each call is one Python procedure call
that batches many records: node results as LOG records with attributes, and one span per node with its dbt start and end times.
Make one call per hook or per run, never one per record. The Python call costs about 2.5–3 s of server time against about 0.5 s
for SQL, so batching is required.

Its advantages:

- It gives `SCOPE = icecore`.
- It writes the LOG records with attributes that the spec assumed.
- It writes real custom spans with dbt timings.
- It keeps typed attributes.
- It survives rollback.
- It does not fail when levels are OFF.

**Fallback: E1 through the same temporary-procedure path** (`SYSTEM$ADD_EVENT('icecore.<kind>', attrs)`). Use it where Python
procedures are not allowed or Anaconda packages are not accepted. It keeps typed attributes and rollback safety, but it has no
SCOPE (so it relies on the `icecore.` record-name prefix), no attributes on logs and no custom spans (timings travel as attributes).

**Not recommended:** anonymous blocks and anonymous procedures (routing), and E3.

**Open for Gate 1 and later spikes:**

1. Temporary procedure or persisted procedure: the principle question above.
2. **S3:** dbt threads use separate sessions, so a temporary procedure must be created in the session that calls it. The probes
   always create, call and drop within one `run_query` sequence. Lag, concurrency and hook coverage remain to be measured.
3. Pin the Python package versions, given the anonymous-procedure `snowflake.snowpark` import failure, even though temporary
   procedures were unaffected.
4. Behaviour on dbt Fusion, dbt Cloud and `EXECUTE DBT PROJECT` is not measured here.
5. "Event table missing" (Review Focus 2) cannot be reproduced with the CI role. With no database event table, procedure records
   would go to the account table, as the routing rule says.
6. Whether ICECORE_CI (and, later, the doctor macro) may read the account table through `SNOWFLAKE.EVENTS_VIEWER`.

- The levels-OFF test asserts success (the acceptance criterion) rather than "0 rows land". What landed is recorded.
