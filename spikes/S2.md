# Spike S2: payload limits

Story 144aefb3 (S12). Measured on 31 Oct 2026 in the sandbox, with dbt-core 1.8.10 and dbt-snowflake 1.8.4. Raw measurements
are in `spikes/results/s2.json`. The probe is `integration_tests/macros/spikes/s2_payload.sql` and the tests are in
`integration_tests/tests/spikes/test_s2_payload.py`.

## Method

`s2_payload(run_id, mechanism, size_kb)` emits **one record** through the S1 probes. Its message or attribute is
`size_kb × 1024` ASCII `x` characters.

| Mechanism | Where the payload goes | S1 probe |
|---|---|---|
| `sql_log` | message of a LOG record (`SYSTEM$LOG_INFO`) | `s1_sql_log` |
| `sql_event` | attribute `icecore.payload` of a SPAN_EVENT (`SYSTEM$ADD_EVENT`) | `s1_sql_event` |
| `python_log` | message of a Python LOG record (`logging.info`) | `s1_python` |
| `python_attr` | attribute `icecore.payload` of a Python LOG record (`extra=`) | `s1_python` |

Two choices differ from the plan:

- **`python_attr` was added** to the plan's three mechanisms, because the S1 recommendation (E2) carries node results as Python
  LOG attributes.
- **Every case runs through a temporary procedure** (`via='temp_procedure'`). S1 showed that anonymous statements never reach the
  database's event table, so the anonymous path would measure nothing.

The value travels as a `CALL` argument literal, so a 1024 KB case sends a statement of about 1,048,700 characters.

The suite has two tests:

- `test_s2_payload` runs the plan's sizes 8, 64, 256 and 1024 KB.
- `test_s2_payload_threshold` runs 384, 512, 768 and 960 KB to locate the limits.

A row counts as landed if it appears within 180 s. The 1024 KB cases were checked again more than 30 minutes later and were still
absent.

## Results

**Every call succeeded**, at every size and for every mechanism. No size makes the dbt call fail.

Each cell gives the payload characters that landed, out of those sent. *Intact* means every character arrived; *dropped* means no
row arrived. Landed length is the stored string length.

| Size | sql_log (message) | sql_event (attribute) | python_log (message) | python_attr (attribute) |
|---|---|---|---|---|
| 8 KB | intact (8,192) | intact | intact | intact |
| 64 KB | intact (65,536) | intact | intact | intact |
| 256 KB | intact (262,144) | intact | intact | intact |
| 384 KB | intact | intact | intact | intact |
| 512 KB | intact (524,288) | intact | **truncated: 524,252 + `...`** | intact |
| 768 KB | intact | intact | **truncated: 524,252 + `...`** | intact |
| 960 KB | intact (983,040) | intact | — (not run: the 512 KB truncation already applies) | intact |
| 1024 KB | **dropped**: call ok, no row | **dropped** | **truncated: 524,252 + `...`** | **dropped** |

Read the table as follows:

- **Hard limit per record: between 960 KB and 1024 KB.**
  - Above it, the record is **silently dropped**: no error, no row, nothing in `QUERY_HISTORY` (the `CALL` shows `SUCCESS`).
  - This applies to SQL logs, SQL span-event attributes and Python attributes alike.
  - A Python LOG whose message would exceed the limit is truncated first, so it survives.
- **Python log messages are truncated at 524,252 characters plus `...`** (about 512 KiB).
  - Truncation starts somewhere between 384 KB and 512 KB.
  - No attribute flags the truncation.
  - SQL log messages are not truncated below the drop limit.
- **Attributes keep their full length up to the drop limit, in both SQL and Python.** Large values belong in attributes, not in
  the message.
- **Statement size is not the constraint.** `CALL` statements of 1,048,782 characters ran successfully. The record is lost at
  ingestion, not at the call.
- **Time is flat in size.**
  - dbt wall time per call: SQL about 1.6–2.2 s, Python about 3.8–4.3 s. These include process start-up and create/call/drop.
  - First visibility: 5–21 s whatever the size. Polling runs every 5 s; S3 owns lag.

## Payload cap for the chosen encoding

Gate 1 is expected to choose E2: a Python procedure in the target database, as recommended in S1.

- **Keep the spec default `payload_cap_kb = 64`.** It is far below every limit measured, and ingestion is billed by volume.
- **Apply the cap to every value that can grow:** messages, attributes and samples. On truncation, set a flag attribute, for
  example `icecore.truncated = true` and the original length. Snowflake truncates Python messages silently and drops oversize
  records silently, so icecore must flag truncation itself.
- **Hard ceiling for any user override: 256 KB per record**, summed over the message and all attributes.
  - That leaves headroom under the 512 KiB Python-message truncation and the roughly 1 MB silent record drop.
  - It also covers the record's own envelope (resource attributes, code.* attributes and so on).
  - `payload_cap_kb` values above 256 should be clamped with a warning.
- **Put large structured values in attributes, not in the message.** The message gets truncated at 512 KiB in Python; attributes
  stay whole.
- **Batching (one Python call per hook or run, as S1 recommends) means many records per call.** The limit is per record, not per
  call. This spike did not measure how many records one call can carry; S3 measures volume per run.

## Acceptance criteria

- [x] **Each mechanism and size: call success and landed length recorded in `s2.json`.** Keys are `<mechanism>.<size_kb>` for
  sizes 8, 64, 256 and 1024 KB, and `threshold.<mechanism>.<size_kb>` for 384, 512, 768 and 960 KB. Each key holds `call_ok`,
  `landed_rows`, `landed_len`, `payload_chars`, `intact`, `dbt_wall_s` and `run_id`.
- [x] **Any size: the dbt call does not fail.** All 28 calls returned success, including the cases where the record was dropped.
- [x] **S2.md names the payload cap for the chosen encoding.** Default 64 KB, hard ceiling 256 KB per record, truncation flagged
  by icecore (section above).

## Test runs

`test_s2_payload`: `3 failed, 13 passed in 709.47s`.

- The 3 failures are the 1024 KB sql_log, sql_event and python_attr cases. The call succeeded but no row landed: a silent drop.
  **That failure is the finding.**
- `python_log` at 1024 KB passes because a truncated row lands.

`test_s2_payload_threshold`: `12 passed in 115.37s` for 384, 512 and 768 KB, then `3 passed` for 960 KB (sql_log, sql_event and
python_attr).
