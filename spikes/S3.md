# Spike S3: ingestion lag, concurrency and hook coverage

**Questions.** How long after a `CALL` does an icecore record become visible in the event table? Do 20 concurrent dbt
invocations lose any records or wait on locks? Which dbt commands fire `on-run-start` and `on-run-end`?

**Run.** 31 Oct 2026, sandbox `ICECORE_SANDBOX.SPIKES`, event table `ICECORE_SANDBOX.TELEMETRY.EVENTS`, role
`ICECORE_CI`. dbt-core 1.8.10 / dbt-snowflake 1.8.4 (floor venv) and dbt-core 1.12.6 / dbt-snowflake 1.12.4 (latest venv).
Other agents were using the sandbox at the same time. Raw results: `spikes/results/s3.json`. Probes:
`integration_tests/macros/spikes/s3_hooks.sql`. Tests: `integration_tests/tests/spikes/test_s3_lag_and_hooks.py`.

## Headline

1. **Lag is seconds, not minutes.** Over two bursts of 10,000 records, p95 was **7.73 s** (dbt 1.8.10) and **6.12 s**
   (dbt 1.12.6), and the worst record took **8.73 s**. The worst hook record took **20.3 s**. The plan's bar, p95 under 60 s,
   passes with a wide margin.
2. **No records were lost.** 20 parallel dbt processes × 500 records gave **exactly 10,000 records, 10,000 distinct**, on both
   dbt versions. All 200 CALLs succeeded, with **0 ms** blocked on a transaction and **0 ms** queued.
3. **Every command fires both hooks except `source freshness` on dbt 1.8.10.** On 1.8.10, `dbt source freshness` runs no
   project hooks unless `flags: {source_freshness_run_project_hooks: true}` is set in `dbt_project.yml`; with the flag it fires
   both. On 1.12.6 the flag defaults to true and it fires both.
4. **Recommended defaults:** SLA default grace **1 minute** (2 × 7.73 s = 15.5 s, rounded up to a whole minute) and anomaly
   history delay **1 minute** (see [Recommendations](#recommendations)). `_sla_default_grace_minutes` is now 1.

## Method

**Emission (Gate 1, option B).** Every record is written by CALLing a persisted SQL procedure in the style of `ICECORE_EMIT`:
`ICECORE_SANDBOX.SPIKES.ICECORE_EMIT_S3_<run_id>(events ARRAY)`, `EXECUTE AS OWNER`, one `SYSTEM$ADD_EVENT` per element.
The test creates it and drops it at the end. Each CALL goes through the guard block (`s1_emit_call`). No anonymous emission
and no session-level change.

**Clocks.** Lag uses only Snowflake's clock. The laptop runs about 10.7 s ahead of Snowflake (S4.md).

- `icecore.emitted_at`: the procedure reads `SYSDATE()` (UTC) once when the CALL starts and puts it on every event of that
  CALL.
- "First seen": the `SYSDATE()` of the poll query that first returned the record. The poller reads the event table every 2 s
  (2.13 s median between poll starts in the 1.12.6 burst).
- Lag of a record = first seen − `icecore.emitted_at`. It is an upper bound: the record became visible at some point between
  the previous poll and this one, so the lag is overstated by at most one poll interval (about 2 s).
- Lag against the record's own `TIMESTAMP` (set by `SYSTEM$ADD_EVENT`) is recorded too, as `lag_vs_event_timestamp`. It is
  about 0.3 s smaller.

**Burst.** `s3_burst(run_id, 500, emitter)` sends 500 events in **5 CALLs of 100**. A CALL keeps only its last 128 events
(S2.md), and GATE1.md caps `ICECORE_EMIT` at 100 per CALL. The test starts 20 separate `dbt run-operation s3_burst` processes
at once, each with its own target and log directory. It polls while they run, then waits 60 s and counts again so late or
duplicate records would show. There was one burst per dbt version: the first, then the one re-run the cost budget allows.

**Hooks.** `integration_tests/dbt_project.yml` has:

```yaml
on-run-start:
  - "{{ s3_hook_probe('start') if var('s3_probe', false) else '' }}"
on-run-end:
  - "{{ s3_hook_probe('end') if var('s3_probe', false) else '' }}"
```

Without `--vars '{s3_probe: true, run_id: ...}'` both hooks render empty, so other suites are unaffected.

- `s3_hook_probe(phase)` CALLs the procedure with one event `icecore.s3_hook` carrying `icecore.run_id`, `icecore.phase`,
  `dbt.command` (= `flags.WHICH`), `dbt.invocation_id` and `dbt.version`, and returns `''`, so the hook runs no SQL of its own.
- Each command runs with `--select tag:s3_spike` (`source:s3_spike` for freshness). The resources are a view `s3_model`, a
  `not_null` test on it, a seed `s3_seed`, a snapshot `s3_snapshot` and a source `s3_spike.s3_seed` with `warn_after: 1 day`.
  Each relation is named with the run_id and dropped by the test.
- The default selector excludes the `s3_spike` tag, as it already did for `root_cause_fixture`, so a plain `dbt build`
  never touches these resources.
- `test` first runs the model without `s3_probe`, and `source freshness` first loads the seed, so that the command under
  test has something to read.
- The test waits up to 240 s for both phases. A phase that never lands is recorded as a gap, and the test `xfail`s with the
  reason. It fails outright only if the dbt command itself fails.

**Fusion.** Not measured: no `dbtf` or Fusion binary is installed (`~/.local/bin/dbt` is dbt-core 1.12.5 under pipx).
GATE1.md open item 5 stays open for Fusion.

## Hook coverage

`start` / `end`: the record landed. The number is that record's lag in seconds. The `start` lag is inflated by the command's
run time, because polling starts only after the command returns. `dbt.command` is what `flags.WHICH` returned.

| Command | dbt 1.8.10 | dbt 1.12.6 | `dbt.command` |
|---|---|---|---|
| `build` | start 8.2 / end 5.4 | start 22.4 / end 20.3 | `build` |
| `run` | start 9.1 / end 7.4 | start 8.2 / end 7.3 | `run` |
| `test` | start 9.1 / end 7.2 | start 6.0 / end 5.1 | `test` |
| `seed` | start 5.3 / end 5.2 | start 4.8 / end 3.1 | `seed` |
| `snapshot` | start 5.3 / end 3.0 | start 8.4 / end 7.1 | `snapshot` |
| `source freshness` | **no hook** (nothing in 240 s; command succeeded) | start 6.1 / end 5.3 | `freshness` |
| `source freshness`, with `flags: {source_freshness_run_project_hooks: true}` | start 7.1 / end 5.0 | (the default) | `freshness` |
| Fusion (`dbtf`) | not installed | not installed | |

Keys `hooks.<version>.<command>` in `s3.json`. These are the second run of the hook matrix, after the final probe code. A
first run, with the per-event `SYSDATE()` probe (see finding 5) and a shared target directory, gave the same coverage on
1.8.10. On 1.12.6, `build` and `snapshot` failed in that first run with `[Errno 20] Not a directory` (finding 6). The flag row
was a one-off: the flag was added to `integration_tests/dbt_project.yml` for that run and removed after it. It is recorded
under `hooks.1.8.10.source freshness +flag source_freshness_run_project_hooks`.

In dbt 1.8.10, `source_freshness_run_project_hooks` defaults to `False` (`dbt/contracts/project.py`); in 1.12.6 it defaults to
`True`. The measurement matches the code.

## Lag and concurrency

| | dbt 1.8.10 burst | dbt 1.12.6 burst |
|---|---|---|
| run_id | `f68a0732f5464ea0b57e737a61b16561` | `81e0e05e57004a7fa8f69a1a854210c3` |
| Records / distinct / expected | 10,000 / 10,000 / 10,000 | 10,000 / 10,000 / 10,000 |
| Per emitter | 500 each, all 20 | 500 each, all 20 |
| CALLs (all `ok 100`, all `SUCCESS`) | 100 | 100 |
| CALL server time p50 / max | 817 / 965 ms | 873 / 1,160 ms |
| Transaction blocked / queued | 0 / 0 ms | 0 / 0 ms |
| Emitter dbt wall time (5 CALLs) | 4.8–5.6 s | 4.7–5.2 s |
| Emitters done / first record seen / all seen, from burst start | 13.2 s / not recorded / 15.8 s | 15.9 s / 13.0 s / 18.5 s |
| **Lag p50 / p95 / p99 / max** (n = 10,000) | **5.75 / 7.73 / 8.30 / 8.73 s** | **3.90 / 6.12 / 6.37 / 6.41 s** |
| Lag vs event `TIMESTAMP` p50 / p95 / max | 5.46 / 7.49 / 8.46 s | 3.60 / 5.82 / 6.09 s |
| Records first seen per poll | not recorded | 6,300, then 3,700 on the next poll |

**Sample size.** 20,000 burst records plus 24 hook records (12 command runs with both phases). That is one sandbox, one afternoon, two bursts
about 5 minutes apart, with other agents' work running.

**Visibility comes in batches.** In the 1.12.6 burst, all 10,000 records appeared in two polls 2 s apart. In the 1.8.10 burst
the poll that saw the first record already saw all 10,000. So at this volume lag looks like a flush cycle of a few seconds,
not a queue that grows with volume. The spread of per-record lag comes mostly from when each emitter ran.

In the 1.8.10 burst, `poll_interval_s_p50` = 60.68 is wrong. That version of the test kept a time only for polls that returned
rows, and it included the 60 s settle re-read. The test was fixed before the 1.12.6 burst: monotonic time at the start of
every timed poll, settle re-read excluded, and `visibility_batches` / `seconds_to_first_seen` added. The lag values of the
first burst are not affected, because first seen comes from the poll query itself.

## Findings

1. **`source freshness` on dbt 1.8 needs a behaviour flag for hooks.** Without
   `flags: {source_freshness_run_project_hooks: true}`, a 1.8 user's freshness runs send nothing through `on-run-end`. UC1
   should document this, and `doctor` can warn when the flag is false. Only 1.8.10 (false) and 1.12.6 (true) were checked;
   the version where the default changed was not.
2. **`flags.WHICH` is `freshness` for `dbt source freshness`**, not `source freshness` or `source-freshness`. A reader that
   matches on the command must use `freshness`.
3. **`OBSERVED_TIMESTAMP` is NULL on icecore records.** All 10,000 SPAN_EVENT rows and the 100 SPAN rows of the 1.12.6 burst
   have `OBSERVED_TIMESTAMP` and `START_TIMESTAMP` NULL (`observed_timestamp` in `s3.json`). The spec's S3 method
   (`OBSERVED_TIMESTAMP − TIMESTAMP`) and its "lag-aware views (`observed_at` vs `TIMESTAMP`)" are not available for
   `ICECORE_EMIT` records. Lag can only be measured from outside, as done here, and history readers need a fixed delay.
4. **Each CALL also writes one SPAN row**, the procedure's own span: 100 CALLs gave 100 SPAN rows next to 10,000 SPAN_EVENT
   rows. That is about 1% more ingestion at 100 events per CALL, and more for small CALLs, such as one per hook.
5. **Never evaluate a non-constant function per event inside `ICECORE_EMIT`.** A first version of the probe read `SYSDATE()`
   for each event. Each such statement cost about 120 ms (3 events: 0.26 s, so about 12 s for a CALL of 100), against 817 ms
   server time for a whole CALL of 100 once `SYSDATE()` was read once per CALL. Variant extraction and `OBJECT_INSERT` with a
   variable stay cheap. UC5 should keep the procedure's loop free of such calls.
6. **Harness: do not share a target directory between dbt 1.8 and 1.12.** 1.8 writes
   `target/run/.../s3_snapshot.sql/s3_snapshot.sql` where 1.12 needs a directory, and 1.12 then fails the snapshot with
   `[Errno 20] Not a directory`. The S3 hook test uses `target/s3-dbt-<version>`.
7. **dbt 1.12.6 flags `freshness`, `loaded_at_field` and `tags` at the top level of a source** with
   `PropertyMovedToConfigDeprecation`. They stay top-level because dbt 1.8 reads them only there.
8. **Concurrency: no lost records, no duplicates, no lock waits.** The procedure's CALLs from 20 sessions ran side by side.
   CALL server time rose from S1's 0.73 s to 0.82–0.87 s (p50) for 100 events under 20-way concurrency.

## Recommendations

- **SLA default grace: 1 minute.** The rule (spec section 10) is 2 × measured p95, rounded up to a whole minute:
  2 × 7.73 s (the larger of the two bursts) = 15.5 s, which rounds up to 1 minute. `_sla_default_grace_minutes` in
  `macros/control/collect_sla_config.sql` returns 1. The test `test_default_grace_is_twice_the_s3_p95_lag` recomputes it from
  `s3.json`, so a re-run of S3 that moves p95 above 30 s fails that test until the default is updated.
- **Anomaly history delay: 1 minute.** History readers should treat records whose `TIMESTAMP` is less than 1 minute old as not
  yet complete. A delay must cover the worst record, not the p95. The worst lag seen was 20.3 s (a hook record), so 2 × 20.3 s =
  40.6 s, rounded up to 1 minute. Keep it configurable.
- **Headroom.** Both values come from a quiet sandbox. Snowflake does not publish an ingestion-latency guarantee, and the worst
  record took a third of the grace. If silence alerts fire falsely in real accounts, raise the default and re-run S3 there.
  The test recomputes the rule from `s3.json` for that purpose.

## Cost

- Two 10,000-record bursts: one per dbt version, the second being the one allowed re-run.
- Two runs of the hook matrix on each version, plus the one-off flag run: about 2 records per command.
- Two smoke tests of the burst macro: 3 and 100 records.
- Every procedure, view, table and snapshot was named with its run_id in `SPIKES` and dropped. A `SHOW` after the runs found
  no `S3_%` object and no `ICECORE_EMIT_S3%` procedure left.

## Reproduce

```bash
cd integration_tests && source ~/.snowflake/icecore_ci.env
.venv/bin/pytest tests/spikes/test_s3_lag_and_hooks.py -k end_hook -v -rxX          # hook matrix, this dbt version
.venv/bin/pytest tests/spikes/test_s3_lag_and_hooks.py -k "concurrency or lag_p95" -v  # one 10,000-record burst
```
