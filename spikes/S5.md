# Spike S5: zero-scan metadata reliability per table kind

**Question.** Do `INFORMATION_SCHEMA.TABLES.ROW_COUNT` and `SYSTEM$LAST_CHANGE_COMMIT_TIME` reflect a write within 60 seconds, for each table kind icecore monitors?

**Run.** 30 Oct 2026 (round 2 on 31 Oct: dbt write patterns and the CHANGES fallback), sandbox `ICECORE_SANDBOX.SPIKES`, role `ICECORE_CI`, Snowflake 10.39.101, dbt-core 1.8.10 / dbt-snowflake 1.8.4. Raw results: `spikes/results/s5.json`. Probes: `integration_tests/macros/spikes/s5_metadata.sql`, tests: `integration_tests/tests/spikes/test_s5_metadata.py`.

## Method

For each kind: create the table in `SPIKES` with the `run_id` in its name, read metadata on the empty table, write 100 rows with `s5_write` (one `INSERT ... SELECT` from `GENERATOR`), read metadata right after the write (t0, about 2 s later because of the dbt invocation) and again 60 s after the write (t60), then drop the table.

`s5_metadata(relation)` runs one query: `SYSTEM$LAST_CHANGE_COMMIT_TIME('<relation>')` left-joined to `<db>.INFORMATION_SCHEMA.TABLES` on schema and name. `relation` is a fully quoted three-part name; the macro splits it into its unquoted parts for the `INFORMATION_SCHEMA` filter.

Dynamic table: `TARGET_LAG = DOWNSTREAM`, `INITIALIZE = ON_CREATE`, over a standard source table. The 100 rows are written to the source, then `ALTER DYNAMIC TABLE ... REFRESH`; metadata is read on the dynamic table.

"Reliable at once" means the first read after the write (t0, ~2 s) already matched; the t60 read returned the same values. Neither source lagged in any measured case.

## Findings

1. **`SYSTEM$LAST_CHANGE_COMMIT_TIME` is a nanosecond epoch token.** It returned values like `1793400450713000001`: the commit time in nanoseconds since the Unix epoch (UTC). The last digits are not significant (after DML the token ended in `…001`, after CTAS and CREATE OR REPLACE in `…000`), so readers convert it at millisecond precision and only compare tokens for order. `TO_TIMESTAMP_NTZ(token, 9)` gives the commit time and matches `INFORMATION_SCHEMA.TABLES.LAST_ALTERED` to the millisecond after a DML write.
2. **The token is `0` for a table that was created but never written.** Readers must turn `0` into "no change yet" (NULL), not into 1970-01-01. `LAST_ALTERED` is set at creation instead, so it cannot tell "created" from "written".
3. **Dynamic tables report their refresh, not their source.** The change time is the refresh commit, and an `INITIALIZE = ON_CREATE` table already has a non-zero token while empty. A freshness monitor on a dynamic table therefore measures refresh freshness; upstream staleness is visible only on the source. Whether a refresh that changes no rows moves the token was not measured.
4. **`adapter.quote` does not escape embedded double quotes.** `adapter.quote('Mixed Case "Orders" …')` returned `"Mixed Case "Orders" …"`, which is invalid SQL. The same holds for `Relation.quoted`. Package macros must double embedded quotes (`replace('"', '""')`) before quoting, and must filter `INFORMATION_SCHEMA` on the raw, case-preserved identifier.
5. **`SYSTEM$LAST_CHANGE_COMMIT_TIME` accepts the fully quoted name** (embedded quotes doubled, passed as an escaped string literal), so the quoted-identifier case needs no special handling beyond finding 4.

## Fallback: `COUNT(*)` over `CHANGES`

For a kind flagged above (today only Iceberg, unmeasured), the readers count rows from the change stream instead of trusting metadata:

```sql
-- requires CHANGE_TRACKING = TRUE on the table, or on the view and its base tables
select count_if(metadata$action = 'INSERT') - count_if(metadata$action = 'DELETE')
from <relation>
  changes (information => default)
  at (timestamp => <last observed time>)
```

It yields the net rows added since that time (a delta, not a total), so it is a separate metric (`rows_added`) from the metadata `row_count`.

Measured (`test_s5_changes_fallback`, result cache off, scan figures from `QUERY_HISTORY_BY_SESSION.BYTES_SCANNED` and `GET_QUERY_OPERATOR_STATS` TableScan pruning):

| Query on a 1,000,100-row change-tracked transient table (11 micro-partitions), 100 rows inserted after `since` | Result | Bytes scanned | Partitions scanned / total |
|---|---|---|---|
| `count(*)` | 1,000,100 | 0 (answered from metadata) | none |
| `count(*) where note like '%-%'` (forced full scan) | 1,000,100 | 35,471,872 | 11 / 11 |
| `count(*)` over `CHANGES ... AT (since)` | 100 | 4,096 | 1 / 1 |
| `count(*)` over `CHANGES` on a view created with `CHANGE_TRACKING = TRUE` over that table | 100 | 4,096 | 1 / 1 |
| `count(*)` over `CHANGES` on a view without change tracking (over an untracked table) | error `091930: Change tracking is not enabled or has been missing for the time range requested` | n/a | n/a |

So the CHANGES count reads only the micro-partitions written since `since`, here 1 partition and 4 KB against 11 partitions and 35 MB for a full scan. It only works when change tracking is on for the table, or for the view and its base tables, and covers the whole window.

What this does not cover:

- **Views without change tracking:** the fallback fails, so they are not supported for zero-scan volume (their `ROW_COUNT` is NULL as well). The readers should say so once, clearly, and not attempt CHANGES.
- **External tables:** **unverified.** The sandbox has no external stage, and the package may not create one. The metadata reader treats them like views (unsupported).
- **Iceberg:** unmeasured both ways, as above.

Until the Iceberg run is done, UC2 readers treat Iceberg as a fallback kind.

## Recommendation for UC2

- `get_row_count_metadata` and `get_last_change_time` trust `INFORMATION_SCHEMA.TABLES.ROW_COUNT` and `SYSTEM$LAST_CHANGE_COMMIT_TIME` for standard, transient and dynamic tables, with no delay.
- Iceberg goes through the `CHANGES` fallback until an external volume is available in the sandbox and this spike is rerun with `ICECORE_EXTERNAL_VOLUME` set.
- The delta from `CHANGES` is a separate metric from the metadata total; never mix them in one history.
- Views and external tables: unsupported for zero-scan volume, with one clear message.
- Token `0` → NULL; quote with doubled embedded quotes.
